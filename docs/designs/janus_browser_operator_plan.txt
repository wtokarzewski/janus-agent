JANUS BROWSER OPERATOR — MVP IMPLEMENTATION PLAN

Goal
Build a lightweight browser automation layer for Janus that controls a real Chrome profile through a custom Chrome extension, instead of using Playwright as the main shopping/research runtime.

Primary goals
1. Make Chrome the first-class target.
2. Use a dedicated persistent browser profile for Janus.
3. Keep the agent on top of a small action protocol, not raw DOM or CSS selectors.
4. Start with a read-only / low-risk interaction model suitable for shopping, research, search, and simple navigation.
5. Keep architecture simple, local, and easy to debug.

Non-goals for MVP
1. No cloud relay.
2. No OpenClaw dependency.
3. No remote CDP.
4. No payment / checkout automation.
5. No generic visual “computer use” based on screen coordinates.
6. No multi-browser abstraction layer yet.
7. No full test framework.

High-level architecture
1. Janus Core
   - Plans next browser actions.
   - Calls a local browser bridge tool.
   - Consumes structured page snapshots.

2. Browser Bridge (local service)
   - Runs locally on the same machine as Chrome.
   - Exposes a simple HTTP or WebSocket API.
   - Sends commands to the Chrome extension.
   - Applies safety rules and validates responses.

3. Chrome Extension
   - Installed only in a dedicated Janus Chrome profile.
   - Performs actual page operations in the active tab.
   - Creates structured snapshots of visible, relevant DOM elements.
   - Returns results to the bridge.

4. Dedicated Chrome profile
   - Separate from your personal profile.
   - Persistent across runs.
   - Used only for Janus tasks.

Runtime flow
User request
-> Janus intent parser
-> shopping/research workflow planner
-> browser bridge command
-> extension action in Chrome
-> result / snapshot back to bridge
-> normalized result back to Janus
-> final answer to user

Core product decision
Do not make Janus think in CSS selectors.
Make Janus think in page snapshots with numbered or stable element references.

Example mental model
- e1: search input “Szukaj”
- e2: button “Szukaj”
- e3: product “Lavazza Crema e Aroma 1kg”
- e4: price “49,99 zl”
- e5: product “Dallmayr Prodomo 500g”
- e6: price “23,49 zl”

Janus should plan with actions like:
- click e1
- type into e1 “lavazza 1kg kawa ziarnista”
- press Enter
- wait for results
- capture snapshot
- extract products and prices

Recommended repository structure
apps/
  janus-core/
  browser-bridge/
  chrome-extension/
packages/
  browser-protocol/
  browser-types/
  browser-snapshot/
  browser-policy/
  browser-workflows/

Suggested responsibilities by package
1. browser-protocol
   - Request/response message schema.
   - Command names.
   - Event names.
   - Runtime validators.

2. browser-types
   - Shared TypeScript interfaces.
   - Snapshot types.
   - Action result types.
   - Error types.

3. browser-snapshot
   - Logic for building and filtering snapshot objects.
   - Scoring and pruning low-value DOM nodes.
   - Text normalization.

4. browser-policy
   - Allowed actions.
   - Denied actions.
   - Domain rules.
   - “read-only by default” safety policy.

5. browser-workflows
   - Higher-level flows such as search product, extract listing, compare offers.

Main MVP components
1. Browser Bridge
2. Chrome Extension
3. Snapshot model
4. Janus browser tool wrapper
5. Initial shopping workflow

PHASE 2 — BUILD THE CHROME EXTENSION

Objective
Create the minimal extension capable of receiving commands and acting on the active tab.

Manifest V3 structure
1. manifest.json
2. background.ts
3. content.ts
4. shared messaging helpers

Minimum permissions
1. activeTab
2. scripting
3. storage
4. tabs
5. host_permissions for sites you want to automate, or broad permissions during development

Manifest outline

{
  "manifest_version": 3,
  "name": "Janus Browser Operator",
  "version": "0.1.0",
  "permissions": ["activeTab", "scripting", "storage", "tabs"],
  "host_permissions": ["<all_urls>"],
  "background": {
    "service_worker": "background.js",
    "type": "module"
  },
  "content_scripts": [
    {
      "matches": ["<all_urls>"],
      "js": ["content.js"],
      "run_at": "document_idle"
    }
  ]
}

Background script responsibilities
1. Accept commands from the bridge.
2. Resolve active or target tab.
3. Route the command to the content script.
4. Handle tab-level operations like open, focus, close, navigate.
5. Return results.

Content script responsibilities
1. Build page snapshots.
2. Resolve element reference IDs.
3. Execute click, type, extract, scroll, and wait actions.
4. Return normalized results.

Do not implement everything at once.
Recommended extension order:
1. ping
2. getCurrentUrl
3. snapshot
4. click
5. type
6. pressKey
7. scroll
8. waitFor
9. screenshot

PHASE 3 — BUILD THE SNAPSHOT SYSTEM

Objective
Expose a compact, AI-friendly map of the page.

Do not dump full DOM.
Do not expose raw HTML as the default view.

Snapshot inclusion rules for MVP
Include:
1. visible buttons
2. visible links
3. visible inputs
4. textareas
5. selects
6. visible price-like text nodes
7. visible product title-like nodes
8. key headings and labels

Exclude:
1. hidden elements
2. tiny layout wrappers
3. repeated decorative spans
4. scripts and styles
5. irrelevant containers

Snapshot generation heuristics
1. Element must be visible in viewport or near viewport.
2. Element text must be meaningful after trimming.
3. Interactive elements always qualify if visible.
4. Certain patterns should infer semanticType.

Useful semantic inference heuristics
1. Inputs with placeholder containing “szukaj” or “search” -> searchInput
2. Text matching currency patterns -> price
3. Links or headings inside listing cards -> productTitle
4. Button text like “kup”, “dodaj”, “szukaj”, “filtruj” -> button or filter

Example semantic price detection regex idea

const PRICE_REGEX = /(\d+[\.,]\d{2})\s?(zl|pln|zł|eur|€)/i;

Example search input detection idea

const SEARCH_HINT_REGEX = /(szukaj|search|czego szukasz)/i;

Snapshot output format recommendation
Use stable synthetic element IDs like e1, e2, e3 per snapshot.
Do not reuse IDs across snapshots as long-term identifiers.
Treat them as snapshot-local references.

PHASE 4 — BUILD THE BROWSER BRIDGE

Objective
Create a local service Janus can call, without talking directly to extension internals.

Recommended technology
- TypeScript
- Node.js
- Fastify or Express
- WebSocket optional, HTTP is enough for first MVP

Bridge responsibilities
1. Accept API requests from Janus.
2. Forward commands to the extension.
3. Correlate request IDs.
4. Apply policy checks.
5. Apply timeouts.
6. Log all browser actions.
7. Normalize errors.

Bridge API suggestion
1. POST /command
2. GET /health
3. GET /sessions/current
4. GET /tabs
5. GET /logs/recent

Recommended request shape

{
  "command": "snapshot",
  "tabId": 123,
  "payload": {}
}

Recommended response shape

{
  "ok": true,
  "commandId": "cmd_123",
  "result": {
    "url": "https://allegro.pl/listing?string=lavazza",
    "title": "Allegro - oferty",
    "elements": []
  }
}

Communication between bridge and extension
You have two main options:
1. Extension polls local bridge.
2. Bridge talks directly to extension via Native Messaging.

Recommended MVP choice
Start with a simple local WebSocket or polling model that is easiest to debug.
Native Messaging is powerful but adds setup overhead.

Practical MVP approach
1. Extension opens a WebSocket to ws://127.0.0.1:<port>
2. Bridge sends browser commands over that socket.
3. Extension returns action results.

Example message envelope

{
  "id": "cmd_abc123",
  "type": "command",
  "command": "click",
  "tabId": 123,
  "payload": { "elementId": "e12" }
}

PHASE 7 — SHOPPING WORKFLOW MVP

Objective
Support the first real use case: product search and offer comparison.

MVP shopping flow
1. Open target marketplace homepage or search page.
2. Capture snapshot.
3. Find search input.
4. Type query.
5. Submit search.
6. Wait for results page.
7. Capture snapshot.
8. Extract top visible product titles and prices.
9. Normalize prices.
10. Return ranked offers.

First supported scenarios
1. Generic product search on Allegro.
2. Generic product search on one or two normal stores.
3. Generic product search through a search engine fallback.

Shopping-specific parsing helper goals
1. Identify title candidates.
2. Identify price candidates.
3. Group title and price by proximity or shared container.
4. Return normalized offer list.

Suggested normalized offer type

type ExtractedOffer = {
  title: string;
  priceValue?: number;
  currency?: string;
  href?: string;
  shippingText?: string;
  source?: string;
};

Example extraction strategy
1. Find all visible productTitle candidates.
2. Find all visible price candidates.
3. Group by nearest shared listing card ancestor if possible.
4. If not, group by spatial proximity.

PHASE 8 — WAIT MODEL AND RELIABILITY

Objective
Make automation stable enough to use daily.

Required wait primitives
1. Wait for URL pattern.
2. Wait for at least N matching meaningful elements in snapshot.
3. Wait for DOM stability for X ms.
4. Wait for visible text.

Do not rely only on fixed delays.
Use fixed delays only as fallback.

Example wait condition type

type WaitCondition =
  | { type: 'urlMatches'; pattern: string; timeoutMs?: number }
  | { type: 'elementExists'; text?: string; semanticType?: string; timeoutMs?: number }
  | { type: 'textVisible'; text: string; timeoutMs?: number }
  | { type: 'domStable'; stableForMs?: number; timeoutMs?: number }
  | { type: 'timeoutOnly'; timeoutMs: number };

Reliability checks after each action
1. Did URL change?
2. Did snapshot change meaningfully?
3. Did expected element disappear?
4. Did a popup or modal appear?
5. Did a CAPTCHA appear?

PHASE 13 — RECOMMENDED MVP DEFINITION

MVP is complete when all of the following are true:
1. Janus can control a dedicated Chrome profile through your extension.
2. Janus can open pages, capture snapshots, click, type, scroll, wait, and screenshot.
3. Janus can search a product on Allegro in a real browser tab.
4. Janus can extract a useful set of visible titles and prices from a results page.
5. Dangerous purchase-like actions are blocked by policy.
6. Failures are logged with enough detail to debug.

Minimal content script snapshot pseudocode

function buildSnapshot() {
  const all = Array.from(document.querySelectorAll('body *'));
  const visible = all.filter(isVisible);
  const relevant = visible.filter(isRelevant);

  return relevant.map((el, index) => ({
    id: `e${index + 1}`,
    tag: el.tagName.toLowerCase(),
    role: el.getAttribute('role') || undefined,
    text: normalizeText(el.textContent || ''),
    ariaLabel: el.getAttribute('aria-label') || undefined,
    placeholder: (el instanceof HTMLInputElement || el instanceof HTMLTextAreaElement)
      ? el.placeholder || undefined
      : undefined,
    href: el instanceof HTMLAnchorElement ? el.href : undefined,
    inputType: el instanceof HTMLInputElement ? el.type : undefined,
    visible: true,
    enabled: !isDisabled(el),
    interactive: isInteractive(el),
    semanticType: inferSemanticType(el),
    rect: getRect(el)
  }));
}

Minimal bridge command handling pseudocode

app.post('/command', async (req, res) => {
  const command = req.body;
  const policy = checkPolicy(command);

  if (!policy.allowed) {
    return res.status(403).send({ ok: false, error: policy.reason });
  }

  const result = await sendCommandToExtension(command);
  res.send({ ok: true, result });
});

Minimal Janus shopping workflow pseudocode

async function searchProduct(query: string) {
  await browser.openUrl('https://allegro.pl');
  let snapshot = await browser.snapshot();

  const searchInput = findSearchInput(snapshot);
  if (!searchInput) throw new Error('Search input not found');

  await browser.click(searchInput.id);
  await browser.type(searchInput.id, query, true);
  await browser.pressKey('Enter');
  await browser.waitFor({ type: 'domStable', stableForMs: 1200, timeoutMs: 10000 });

  snapshot = await browser.snapshot();
  return extractOffers(snapshot);
}

Practical engineering advice
1. Keep the first transport stupid simple.
2. Do not prematurely optimize around CDP or native messaging.
3. Do not try to solve every website at once.
4. Make Allegro the first real target, but keep abstractions generic.
5. Build strong logs before fancy features.
6. Build snapshot quality before action quantity.
7. Keep dangerous actions blocked until you have confidence.

Final recommendation
The right MVP is not “full browser automation.”
The right MVP is “safe browser operator for shopping and research in a real Chrome profile.”

If you stay disciplined on that scope, this will be implementable quickly and it will solve the actual problem you care about.
